# HEWL performance: A64FX and provisional mini05 x86 reference

## Outcome and scope

The native ARM scaling and coupled tests passed, and the matching mini05 CPU
tests passed with an **experimental rc3 x86 image**. A finalized, reproducibly
built x86 GROMACS 2026.3 container remains a near-term deliverable, as requested
by the user. These results compare the delivered implementations on these two
machines; they cannot isolate the instruction set, compiler or storage alone.

| Experiment | Execution | Result |
|---|---|---|
| ARM fixed-TPR MD, 4/8/16/24/48 CPUs, two repeats each | 2160455, cna0002, 16:41 | Passed all ten 5-ps observations |
| ARM two all-site CpHMD cycles, 16/4/8 CPUs, one observation each | 2160456, cna0003, 18:55 | Passed all three independent cycle audits |
| Paired serial DelPhi/PETIT component tests | ARM 2160475, 21 s; mini05 sequential shell launcher | Three repeats/component; accepted inputs and numerical output |
| x86 MD, four/six physical cores, two repeats each; coupled four cores | mini05, rc3 image | Passed four MD observations and one two-cycle audit |
| Targeted ARM startup probe | 2160496, cna0003, 3:43 | Passed zero-step default/reproducible probes and two audited 5-ps observations |

All runs use the existing HEWL 4LZT Amber14SBpH/TIP3P snapshot, pH 6, 310 K and
the tighter copied PB profile. No canonical controller, force-field, solver
executable or candidate image is changed. The default generated scheduler's
walltime-guard defect remains deferred; these are bounded direct harness jobs
with no automatic successor. Coupled fixtures explicitly use a 2700-second
cycle guard, well inside their 90-minute allocation.

## Component timings: protect the original DelPhi baseline

Two representative titration states, Asp and N-terminus, each supply a model,
protein-coarse and protein-focus solve. All 14 solver input files match the
earlier accepted scientific manifest. The identical PETIT energy table is also
frozen. Focus reads the phi map generated by that architecture's preceding
coarse solve. One CPU is pinned; three fresh-process repeats use the same Bash
launcher in both containers. Individual timings exclude container startup and
include the small GNU `date`/process overhead.

| Component | x86 median seconds | ARM median seconds | ARM / x86 time |
|---|---:|---:|---:|
| Asp model | 0.2974 | 0.3837 | 1.29 |
| Asp coarse protein | 0.1641 | 0.4116 | 2.51 |
| Asp focus protein | 0.4221 | 1.0813 | 2.56 |
| NTR model | 0.2892 | 0.3850 | 1.33 |
| NTR coarse protein | 0.1664 | 0.4098 | 2.46 |
| NTR focus protein | 0.4505 | 1.2821 | 2.85 |
| PETIT, fixed table, seed 1729, 1000/100000 MC steps | 0.1414 | 0.7477 | 5.29 |

Ranges and all raw observations are retained in `component-comparison.json`.
Above one means ARM took longer on these machines. These results justify
preserving the original x86 executable before any compiler experiment; they
do not prove an ARM compiler regression independent of the hardware.

Five PB cases have the same **last reported** iteration count; Asp coarse
reports 90 on x86 and 100 on ARM. The two coarse cases meet the requested
reported maximum-residual criterion. The four model/focus cases reach the
500-iteration cap above `maxc=0.0001`, preserving the earlier convergence caveat.
The selected scalar energy terms agree at their printed four-decimal precision;
this is not byte identity of full energy tables or proof of absolute convergence.
Matched-input/seed PETIT means differ by at most **0.001340002**, with different
final microstates. All distributions/state inventories are valid. This is below
the earlier 0.02 engineering occupancy screen, without establishing statistical
equivalence or physical pKa accuracy.

## MD scaling and the cost outside the integration timer

Median seconds for an identical 5-ps TPR, two timing observations/count:

| Machine / CPUs | Whole command | GROMACS reported time | Difference | Reported ns/day |
|---|---:|---:|---:|---:|
| mini05 / 4 | 27.678 | 25.528 | 2.151 | 16.927 |
| mini05 / 6 | 20.415 | 18.008 | 2.407 | 23.995 |
| A64FX / 4 | 154.187 | 109.352 | 44.835 | 3.952 |
| A64FX / 8 | 101.613 | 56.780 | 44.834 | 7.610 |
| A64FX / 16 | 76.043 | 31.157 | 44.886 | 13.868 |
| A64FX / 24 | 83.491 | 22.144 | 61.347 | 19.514 |
| A64FX / 48 | 76.174 | 14.715 | 61.459 | 29.366 |

At four physical cores, ARM takes **5.57 times** the whole-command time and
**4.28 times** the reported GROMACS time. For this short experiment the fastest
observed ARM whole-command median is at 16 CPUs. Forty-eight CPUs maximize
integration throughput, while process overhead erases much of the short-run
benefit. Two timing repeats and this particular 5-ps duration do not establish
a universal optimum or long-run production ns/day.

The original raw x86 `md/summary.json` inherited an ARM-specific sentence about
48 reserved CPUs. That sentence is a metadata error: mini05 used physical
CPUs 0–5 and had no Slurm reservation. Raw evidence is preserved; the normalized
`workflow-comparison.json` explicitly corrects it, and the current helper uses
a generic accounting note. Timing/scientific fields are unaffected.

## Whole CpHMD cycle costs

One observation/count, two complete all-site cycles with 100 relaxation and
1000 effective steps/cycle. Every protonation vector/dictionary transformation,
PB/MC inventory, four disulfides, atom order, finite energy series and finalized
segment/restart is checked independently. Subsequent trajectories/protonation
states can differ across architectures; initial coordinates are identical.

| Two-cycle measurement | x86 4 CPUs | ARM 4 CPUs | ARM 8 CPUs | ARM 16 CPUs |
|---|---:|---:|---:|---:|
| Whole controller seconds | 102.447 | 434.934 | 354.613 | 316.906 |
| PB driver, includes preparation/parallel solves/postprocessing | 67.752 | 134.742 | 76.617 | 52.446 |
| PETIT wrapper | 0.299 | 1.504 | 1.503 | 1.474 |
| Topology update wrapper | 0.185 | 0.315 | 0.317 | 0.317 |
| Relaxation MD commands | 5.501 | 94.902 | 93.096 | 90.979 |
| Effective MD commands | 14.646 | 133.786 | 113.444 | 101.818 |
| Other controller, preprocessing, preflight and I/O | 14.065 | 69.685 | 69.636 | 69.872 |

The equal-four-core controller ratio is **4.25**. The stage timers deliberately
avoid double-counting GROMACS conversions nested inside the PB wrapper.
MD-stage clocks include executable startup and retained diagnostic copies;
they are not integration-kernel timings. Whole controller time excludes the
subsequent independent audit, but includes the fixture's retention overhead.
Storage differs (Deucalion project filesystem versus mini05 home NFS). These
are useful integration-cost screens, not uninstrumented production forecasts.
More ARM CPUs accelerate PB's independent site jobs; this does not negate the
slower serial solver observations. PLUMED calculations and optional multi-solute
`fixgro` paths are not active in this HEWL protocol and have no performance
claim here. Small PB helper costs remain aggregated inside the PB driver.

## Startup follow-up

The direct MD screen has no cycle-retention wrapper, yet repeats show roughly
45/61 seconds outside GROMACS's reported time. Source inspection used the exact
SHA-pinned upstream 2026.3 tarball. `parallel_3dfft.cpp` selects
`FFT5D_NOMEASURE` for reproducible setup, and `fft5d.cpp` selects FFTW_ESTIMATE
instead of FFTW_MEASURE. Job 2160496 compares default/reproducible zero-step
starts, followed by two independently audited 5-ps `-reprod` runs. The diagnostic
does not change the candidate or promote a production setting. Its accepted result is
recorded alongside the main evidence. The accepted measurements are:

| Eight-thread observation | Default | `-reprod` |
|---|---:|---:|
| Zero-step whole command | 45.492 s | 16.281 s |
| 5-ps whole command, median of two | 101.613 s | 72.770 s |
| 5-ps reported GROMACS time | 56.780 s | 56.661 s |

Whole-command time falls **28.4%**, with nearly unchanged reported integration
time and all 51 frames/finite energies/atom-order/disulfide checks passing.
The zero-step comparison shares one exclusive node; the original 5-ps default
screen ran on another A64FX node. The result is consistent with a substantial
FFT-planning contribution, supported by the checksum-pinned source path.
About **16.1 seconds** still remain outside reported integration time; they are
not attributed by this experiment. [FFTW's planner documentation](https://www.fftw.org/fftw3_doc/Planner-Flags.html)
explains the measured-versus-estimated plan tradeoff. Other optimizations also
change with `-reprod`. No production setting is promoted: validate the candidate
configuration through coupled/RT/continuation gates and representative longer
runs before recommending it. Raw data and normalized interpretation are in
`startup-2160496/` and `startup-comparison.json`.

## Failure preservation and security

Initial component preflight 2160467 failed its numerical audit because the
new harness passed the parameter file through stdin. DelPhi expects the
filename as an argument, just as the canonical driver supplies. It emitted
FORTRAN STOP but returned zero; the missing-energy check rejected the run.
The corrected paired launcher uses the actual protocol. That failed experiment,
the older x86 image's missing Python interpreter, and the first tar directory
metadata warning remain documented. They are not counted as accepted results.

Source freezers run the repository credential/artifact guard, copy allowlisted
regular scientific text, exclude Git metadata/ELF/ignored local files, and hash
each file. The SIF and simulation inputs are transferred/verified separately.
All Deucalion scratch/temp/results stay in the authorized project. Final quota
output reports 9.74G group usage under the default quota policy; the raw report
is saved, without inferring remaining project capacity from zero/default fields.
No benchmark jobs remain queued or running. No secrets,
SIF, trajectory, binary or archive is selected for Git; only compact text
evidence is selected. Full archives remain outside Git and are checksum checked
after download. Archive extraction restores regular files only, not diagnostic
symlinks targeting container paths. Pattern checks are not malware or complete
Git-history certification.
